## 4. 触发方式（含踩坑记录）

**最初尝试（失败）**：把 `lifecycle.max_uptime_hours` 调成 `0.1` 想快速命中硬上限。
等待 4.5 分钟无任何动作。根因见 `core/config.py:404-409`：

```python
biggest = max(x["after_hours"] for x in lc["levels"])
if max_h < biggest:
    issues.append(f"lifecycle.max_uptime_hours({max_h}) < 最大等级阈值({biggest})，已提升")
    max_h = biggest          # ← 0.1 被抬回 720
```

即 `max_uptime_hours` **不得低于最高等级阈值**，因此「调小硬上限触发 deadline 强制睡眠」
这条路径在实机上不可达。**改用等级驱动的 `force_sleep`**：

```
临时配置：dry_run=false、sleep_duration_min=1、
          levels[0].action = "force_sleep"（L0，after_hours=0）
```

`resolve_level(6.9h)` → L0 → `action=force_sleep` → 立即强制睡眠，无需等硬上限。

## 7. 发现的问题

### P1（已修）`config.issues` 被收集但无人消费 —— 非法配置静默生效

`core/config.py` 的 `validate()` 会把非法值回退、阈值抬高、参数夹取等写入 `self._issues`，
但全仓库**没有任何地方读取 `config.issues`**（`grep -rn "\.issues"` 为空）。
后果：用户把 `max_uptime_hours` 写成 `30`（想改成 30 小时）或非法值时，插件会静默改回/抬高，
日志与 WebUI 毫无提示 —— 核心承诺「30 天必定真睡一次」被悄悄改写而运维不可见。
本次实机就是这样浪费了 4.5 分钟排查。

**修复**：`SafetyGuard.self_check()` 把 `config.issues` 逐条并入告警清单，
从而同时出现在①启动日志（`启动告警：…`）与②`/guardian safety` 命令输出。
回归用例：`tests/test_adversarial.py::test_config_normalization_issues_are_surfaced_by_self_check`。

### P2（观察项，未改）睡眠动作先 flush 再记账

`actions/sleep.py:83` 在 `safety.commit()`（由 `engine.request_sleep` 随后调用）之前
就执行了 `state.flush(force=True)`。若进程恰好在该窗口崩溃，本次睡眠的冷却/配额记录会丢失
（服务本身已恢复，只是记账缺失）。影响很小，但严格来说记账应晚于副作用完成。
建议后续把 flush 收到 `commit()` 之后。

### 非缺陷

- 实机观察到 `qq_login:qq` 由 `unknown` 变 `ok`：探针瞬态（NapCat 状态未就绪），
  且 `PolicyEngine._suggest()` 对 `UNKNOWN` 直接返回 `None`，不会触发动作。
- `max_uptime_hours` 在 schema 中是 `type: int`，故不能用小数；这是配置契约，非缺陷
  （真正的问题是上面的静默 clamp）。
