## 2. 可观测性三层

### 2.1 日志（Logging）

**约定**：统一走 `from astrbot.api import logger`（`astrbot` 容器内即 AstrBot 日志，落 `docker logs astrbot` / journald）。禁止使用 `print`；禁止在日志中打印 `access_token`、完整 UMO、完整 user_id。

| 级别 | 用途 | 示例场景 |
| --- | --- | --- |
| `DEBUG` | 探针取数细节、HTTP 状态、argv（脱敏后） | 排障期临时开启 |
| `INFO` | 生命周期与正常闭环：启动/停止/巡检完成/动作成功/档位切换 | 日常 |
| `WARNING` | 降级但不致命：探针 UNKNOWN、冷却抑制、socket 不可写 | 日常关注 |
| `ERROR` | 动作失败、熔断触发、审计写失败、通知失败 | 需处理 |
| `CRITICAL` | 保留（Guardian 用 FATAL 级通知而非 CRITICAL 日志，避免与日志级别混淆） | — |

**结构化字段约定**（logger 的 `%s` 占位，键值对显式标注）：

```
[guardian] <event> key1=value1 key2=value2 ...
```

**关键日志点清单**：

| 事件 | 级别 | 字段 | 样例行 |
| --- | --- | --- | --- |
| 插件启动 | INFO | `version, mode, profile, dry_run, allowlist` | `[guardian] 启动 version=0.1.0 mode=server profile=normal dry_run=true allowlist=[napcat]` |
| 安全自检 | WARNING | `warn_count` | `[guardian] 安全自检完成 warn_count=2` |
| 巡检完成 | INFO | `trigger, incidents, elapsed_ms` | `[guardian] 巡检完成 trigger=interval incidents=1 elapsed_ms=812` |
| 探针结果 | DEBUG | `probe, target, status, severity` | `[guardian] probe=container_memory target=napcat status=warn mem_mb=740` |
| 动作允许 | INFO | `kind, target, code` | `[guardian] 动作允许 kind=restart_container target=napcat code=ok` |
| 动作抑制 | WARNING | `kind, target, code, reason` | `[guardian] 动作抑制 kind=restart_container target=napcat code=cooldown remain=420` |
| 动作结果 | INFO | `kind, target, ok, elapsed_ms` | `[guardian] 动作完成 kind=restart_container target=napcat ok=true elapsed_ms=7420` |
| 熔断触发 | ERROR | `reason, target` | `[guardian] 熔断触发：窗口内动作数超过每小时上限 6（target=napcat）` |
| 档位切换 | INFO | `profile, actor, night_until` | `[guardian] 档位切换 profile=night actor=u:***1234 night_until=1730000000` |
| 通知发送 | INFO | `severity, umo_masked, dedup` | `[guardian] 通知发送 severity=crit umo=umo:***a1b2c3d4 dedup=false` |

**脱敏**：`qq.access_token` 一律 `mask_token()` → `ab***(N)`；UMO 记 `umo:***<sha1[:8]>`；user_id 记 `u:***XXXX`（末 4 位）（B11 §9）。

### 2.2 状态快照（Snapshot）

`/guardian status` 走 `StateStore.snapshot()`（B11 §3）+ 最近一轮探针结果，输出人类可读文本（§3 模板）。`state.json` 结构示例（B11 §3，字段为权威）：

```json
{
  "schema": 2,
  "mode": "server",
  "profile": "night",
  "night_until": 1730038400.0,
  "cooldown": { "napcat": 1730000900.0 },
  "circuit": { "__global__": [1730000100.0, 1730000400.0], "napcat": [1730000400.0] },
  "last_status": { "container_health/napcat": "ok", "qq_login/qq": "ok", "container_memory/napcat": "warn" },
  "seq": 128,
  "updated_ts": 1730000720.5
}
```

`samples.json`（内存采样窗口，B06）：`{ "napcat": [{"ts": 1730000000.0, "mem_mb": 512.3}, ...] }`。

### 2.3 审计（Audit）

`data/guardian/audit.jsonl`，追加式 JSONL，**不可关**（B00 §10-7），达 `max_bytes` 轮转保留 `.1/.2/.3`（B11 §5）。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `ts` | float | 事件时刻 epoch 秒 |
| `kind` | string | `incident.recorded` / `action.executed` / `action.suppressed` |
| `incident_id` | string | 事件 id（12 hex） |
| `actor` | string | `system` / `u:***1234` / `llm:guardian_restart_container` / `cmd:/guardian restart` |
| `trigger` | string | `interval` / `command` / `llm` / `startup` / `cron` |
| `probe` / `target` | string | 触发探针名 / 容器名·节点名·`qq` |
| `status` / `severity` | string | `ok`·`warn`·`crit`·`unknown` / `info`·`warn`·`crit`·`fatal` |
| `action` / `params` | string·object\|null | 动作 kind / 已 `redact()` 脱敏的参数 |
| `result` / `ok` / `elapsed_ms` | string·bool·int | 结果 detail / 是否成功 / 动作耗时 |
| `suppressed` / `reason` | bool / string | 是否被安全层抑制 / 抑制原因或结论文案 |

**查询示例**：

```bash
# 最近 20 条审计（倒序）
docker exec astrbot tail -n 20 /AstrBot/data/plugin_data/astrbot_plugin_guardian/guardian/audit.jsonl

# 只看被抑制的动作
docker exec astrbot sh -c "grep '\"suppressed\":true' \
  /AstrBot/data/plugin_data/astrbot_plugin_guardian/guardian/audit.jsonl" | tail -n 20

# 用 jq 结构化查询（宿主上对已拷出的文件）
jq -c 'select(.kind=="action.suppressed") | {ts,actor,target,action,reason}' audit.jsonl | tail -n 20
jq -r 'select(.kind|startswith("action.")) | .target' audit.jsonl | sort | uniq -c | sort -rn   # 各目标动作次数
jq -c 'select(.target=="napcat") | {ts,kind,action,ok,reason}' audit.jsonl                       # 某容器时间线
```

## 4. 指标清单（每次巡检采集）

| 指标名 | 来源探针 | 单位 | 正常范围 | 告警判据 | 文档 |
| --- | --- | --- | --- | --- | --- |
| `reachable` | `docker_daemon` | 0/1 | 1 | 0 → UNKNOWN/WARN | B04 §4 |

| `health_unhealthy` | `container_health` | 0/1 | 0 | 1 → CRIT + restart | B04 §5 |

## 5. 故障排查手册（Playbook）

### P1 插件未加载
- **症状**：`/guardian` 无响应；`docker logs astrbot` 无 `[guardian]` 行。
- **快速诊断**：`docker exec astrbot ls /AstrBot/data/plugins/astrbot_plugin_guardian`；`docker logs astrbot 2>&1 | grep -i guardian | tail -n 50`。
- **根因**：插件目录未挂载 / `metadata.yaml` 缺失 / 语法错误 / `requirements.txt` 依赖未装。
- **处理步骤**：① 核对 compose 的插件 bind mount（B13 §3）；② `python -m py_compile main.py` 查语法；③ `docker exec astrbot pip install -r requirements.txt`；④ 重启容器 `docker compose restart astrbot`。
- **预防**：CI 加 `py_compile` + import 冒烟；升级后查 `[guardian] 启动` 日志行（C01-03）。

### P2 socket 权限拒绝
- **症状**：`docker_daemon` 探针 UNKNOWN，日志含 `socket 不可用` / `Permission denied`。
- **快速诊断**：`docker exec astrbot ls -l /var/run/docker.sock`；`getent group docker`；`stat -c '%g' /var/run/docker.sock`。
- **根因**：`group_add` 的 `DOCKER_GID` 与实际 socket 属组不符；socket 未挂载。
- **处理步骤**：① 更新 `deploy/.env` 的 `DOCKER_GID`；② `docker compose up -d astrbot` 重建；③ 复核 `/guardian status` 的 `socket_writable=1`。
- **预防**：部署检查单校验 GID（B13 §4）；重启 docker 后重核 GID。

### P3 NapCat 一直离线
- **症状**：`qq_login` 长期 CRIT；`/guardian status` 显示 QQ 离线。
- **快速诊断**：`docker exec astrbot curl -s http://napcat:3000/get_login_info`；`docker logs napcat | tail -n 50`。
- **根因**：会话失效需扫码；token 错；容器未启动；网络不通。
- **处理步骤**：① 确认 `napcat` 运行；② 打开 NapCat WebUI（6099）人工扫码；③ 核对 `qq.access_token`；④ 触发 `/guardian check`。
- **预防**：`restart_container` 带会话重启（B05 §5）；连续失败 3 次升级 FATAL 提示扫码。

### P4 容器反复重启（重启风暴）
- **症状**：`restart_delta≥3` CRIT；日志频繁 `动作完成 kind=restart_container`。
- **快速诊断**：`docker inspect -f '{{.RestartCount}}' napcat`；`jq -r 'select(.action=="restart_container")|.ts' audit.jsonl | tail`。
- **根因**：容器启动即崩（CrashLoop）；冷却被绕过；健康检查误判。
- **处理步骤**：① 看容器日志找崩溃原因；② 确认 `action_cooldown_sec ≥ 600`、`max_actions_per_hour ≤ 6`；③ 必要时切 `maintenance` 停止自动动作；④ 修根因后再恢复。
- **预防**：CrashLoop 判定 `suggested=None`（B04 §11）；看门狗指数退避（B13 §7.2）；R1 缓解。

### P5 内存持续增长
- **症状**：`growth_mb_per_hour ≥ 80`；`mem_mb` 缓慢逼近 `crit_mb`。
- **快速诊断**：`docker exec astrbot cat .../guardian/samples.json | jq '.napcat[-5:]'`；`docker stats --no-stream napcat`。
- **根因**：应用内存泄漏；缓存无上限；连接未释放。
- **处理步骤**：① 保持 `dry_run=true` 观察曲线；② 开启 `memory.restart_on_leak=true` 走泄漏重启（用 `memory.leak_cooldown`）；③ 定位泄漏点（B06 取证）。
- **预防**：滑动窗口趋势判定；夜间档位预约凌晨维护重启（B00 §5）。

### P6 OOMKilled
- **症状**：`oom_killed=1` CRIT；容器 `State.OOMKilled=true`。
- **快速诊断**：`docker inspect -f '{{.State.OOMKilled}}' napcat`；`dmesg | grep -i oom | tail`（宿主）。
- **根因**：内存超 cgroup 限制被杀；泄漏累积。
- **处理步骤**：① 查 B06 重启前快照 `memory_snapshots_<c>.json`；② 提高容器内存上限或修泄漏；③ 复核 `restart_on_leak` 配置。
- **预防**：`crit_mb` 阈值 + 增长速率双判据；B04 §5 OOM 分支转 B06。

### P7 ROS2 节点缺失
- **症状**：`ros2_nodes` CRIT，`missing` 非空；日志 `节点仍未出现`。
- **快速诊断**：`docker exec astrbot bash -lc 'ros2 node list'`；两侧 `env | grep ROS_DOMAIN_ID`。
- **根因**：域号/RMW/网络不一致（B07 §11 P1–P4）；节点进程崩。
- **处理步骤**：① 核对 `ROS_DOMAIN_ID`/`RMW_IMPLEMENTATION`/`ROS_LOCALHOST_ONLY`；② 配置 `ros2.node_restart_commands` 恢复命令；③ 触发 `/guardian check`。
- **预防**：空图降级 UNKNOWN 不误重启（B07 A3）；`network_mode: host` + `ipc: host`。

### P8 话题 hz 为 0
- **症状**：`ros2_topics` `hz=0` 或 `publishers=0`。
- **快速诊断**：`docker exec astrbot bash -lc 'ros2 topic hz /topic --window 5'`；`ros2 topic info /topic -v`。
- **根因**：事件型话题（无固定频率）；发布者崩溃；QoS 不匹配。
- **处理步骤**：① 从 `expected_topics` 移除事件型话题或 `topic_hz_min=0`；② 配置发布节点恢复命令；③ 复核 `publishers`。
- **预防**：固定 `--window 5`；`topic_hz_min` 取期望值 60%（B07 §12）。

### P9 通知发不出
- **症状**：有 CRIT 事件但用户未收到消息；日志 `通知发送` 缺失或 `umo` 为空。
- **快速诊断**：`jq -c 'select(.severity=="crit")|{ts,target}' audit.jsonl | tail`；检查 `notify.umo_list`。
- **根因**：UMO 未配置/失效；`min_severity` 过高；限流窗口抑制；`qq` 离线。
- **处理步骤**：① 补齐 `notify.umo_list`（从 AstrBot 会话取 UMO）；② 下调 `min_severity`；③ 确认 QQ 在线；④ 手动 `/guardian check` 触发。
- **预防**：UMO 仅来自配置；限流 + 去重 + 档位静默（B08 §7）；R8 缓解。

### P10 cron 不触发
- **症状**：定时重启/夜间维护重启未执行。
- **快速诊断**：`docker exec astrbot date`；`jq -c 'select(.trigger=="cron")' audit.jsonl | tail`；检查 `schedule.daily_restart_cron`。
- **根因**：容器时区与预期不符（R7）；cron 表达式非法；`daily_restart_enabled=false`；调度器任务残留（R10）。
- **处理步骤**：① 核对 `TZ`（compose 环境变量）；② 校验 5 字段 cron；③ 开启开关；④ 热重载后确认无重复定时器。
- **预防**：`TZ=Asia/Shanghai`；cron 以本地时区解释；`terminate()` 严格取消任务。

### P11 事件循环卡顿
- **症状**：`loop_lag_ms` 升高；Bot 响应变慢；`last_scan_age` 超 2×间隔。
- **快速诊断**：`/guardian status` 看 `loop_lag_ms`；`docker logs astrbot | grep -i "整体巡检超时"`。
- **根因**：同步阻塞调用（子进程/DNS/大文件）；探针未走 `to_thread`；并发过高。
- **处理步骤**：① 定位阻塞探针（`probe_timeout` 超时日志）；② 改 `asyncio.to_thread`/`create_subprocess_exec`；③ 降 `max_concurrency`。
- **预防**：全程 async + 超时 + 并发上限（D9/D10）；单探针 8s、整体 30s 兜底（B03 §7）。

### P12 dry_run 忘了关
- **症状**：故障被检出但容器从未被重启；动作 `detail` 以 `[dry-run]` 开头。
- **快速诊断**：`/guardian status` 看 `dry_run`；`jq -c 'select(.kind=="action.executed")|{action,detail:null}' audit.jsonl | tail`。
- **根因**：`dry_run=true` 为默认值（B00 §7），首次部署后未关闭。
- **处理步骤**：① 观察 ≥3 个巡检周期确认判定准确；② 通过 WebUI/配置把 `dry_run` 改为 `false`；③ 热生效后 `/guardian check` 验证一次真实动作。
- **预防**：启动自检提示 `dry_run=true`；上线检查单设「关闭 dry_run」勾选项。

## 8. 上线检查单（Checklist）

### 8.1 部署前

- [ ] `safety.action_cooldown_sec ≥ 600`、`max_actions_per_hour ≤ 6`。

## 9. 回滚方案

### 9.1 插件回滚（代码层）
```bash
docker compose -f deploy/docker-compose.yml stop astrbot
cp -a data data.bak.$(date +%Y%m%d%H%M)                       # 先备份数据
git -C src/astrbot_plugin_guardian checkout <last_good_tag>   # 回到上一稳定版本
docker compose -f deploy/docker-compose.yml up -d astrbot
docker logs -f astrbot | grep -i guardian                     # 确认启动无异常
```
触发条件：升级后 30 分钟内出现「连续重启 ≥3 次」「`/guardian status` 无响应」「事件循环阻塞告警」之一（B13 §13）。

### 9.2 compose 回滚
```bash
cp -a deploy/docker-compose.yml deploy/docker-compose.yml.bak
git -C . checkout <last_good> -- deploy/docker-compose.yml
docker compose -f deploy/docker-compose.yml up -d             # 重建受影响容器
docker compose -f deploy/docker-compose.yml ps                # 核对 Up
```

### 9.3 看门狗停用（自重启关闭）
```bash
# 顺序：先停 timer 再停 service，避免"容器已停、看门狗仍轮询"的日志噪声
sudo systemctl disable --now guardian-watchdog.timer
sudo systemctl stop guardian-watchdog.service
sudo rm -f /etc/default/guardian-watchdog
sudo systemctl daemon-reload
# 同步把插件侧自重启关掉，避免写无效请求
#   safety.allow_self_restart=false  或  safety.self_restart_strategy=disabled
```

### 9.4 数据回滚 / 全量下线
```bash
# 数据回滚（仅状态损坏时；会丢失备份之后的增量事件，B11 §10）
mv data/plugin_data/astrbot_plugin_guardian/guardian{,.broken}
mv guardian.bak.YYYYMMDDHHMM data/plugin_data/astrbot_plugin_guardian/guardian
docker compose restart astrbot
# 全量下线（保留数据卷便于回滚；最后一行不可逆，确认后再执行）
sudo systemctl disable --now guardian-watchdog.timer
docker compose -f deploy/docker-compose.yml down
# docker volume rm guardian-data && rm -rf data napcat/config
```

## 11. 已知限制与明确不做的边界

| 项 | 说明 |
| --- | --- |
| 单机范围 | 仅单机 Docker Compose；不做集群/多主机编排。 |
| 无 WebUI 页面 | 本期以命令 + 通知 + 日志 + 状态文件承载（Roadmap）。 |
| 不做 AstrBot 核心改造 | 不改适配器，不重写平台层。 |
| 不做任意 shell | LLM 永不传入自由命令；恢复命令仅来自配置白名单（B00 §10-1）。 |
| 不做 ROS2 业务编排 | 仅健康探测与节点重启，不做 Service/Action 业务调用。 |
| 重启延迟 | `watchdog` 策略下自重启延迟 ≤ 一个 timer 周期（默认 30s）。 |
| 重登需扫码 | NapCat 会话彻底失效时无法自动恢复，需人工扫码（R3）。 |
| 直挂 socket | 本期默认直挂 `/var/run/docker.sock`（等价 root 权限面），最小权限方案见 Roadmap。 |
| 时区依赖 | cron 与新鲜度校验依赖时钟，漂移会导致误触发（R7）。 |
