## 5.2 30 天保证的形式化论证（B15 §7）

设 `T = lifecycle.max_uptime_hours`（默认 720h）。系统 uptime 单调不减，仅在真睡眠后归零。

1. **若 Bot 在 `[0, T)` 内自主睡眠**：保证成立（已真睡 ≥1 次）——对应 C15-33。
2. **若 Bot 在 `[0, T)` 内从未自主睡眠**：uptime 单调增至 `T`，`force_sleep_on_deadline=true` 使 `evaluate()` 返回 `force_sleep=True`，引擎执行 `SleepAction`——对应 C15-28/34。
3. 因此**无论 LLM 是否配合，30 天内必定发生 ≥1 次真睡眠**（除非 `force_sleep_on_deadline=false` 或 `dry_run=true`，此时降级为强制告警）——对应 C15-25/30。

**边界**：`sleep_targets` 不含本体时 uptime 由 `napcat` 决定（C15-35）；看门狗失效时保证降级为"必定尝试"（C15-44）；时钟回拨致 uptime 变小被检测（C15-41）。

## 5.3 睡眠执行路径（B15 §4 `SleepAction`）

```
execute(spec)
  ├─ dry_run -> 仅记录 "[dry-run] 将睡眠 ..."，零副作用（C15-25）
  ├─ 先发通知（本体可能马上离线）（C15-37）
  ├─ duration_min > 0 -> stop -> sleep(duration*60) -> start（C15-36/59）
  ├─ strategy=watchdog -> 写 restart_request.json（nonce/ts/target）（C15-45）
  ├─ strategy=docker_api -> 先回执后 POST restart（仅本体不在目标内）（C15-47）
  └─ on_sleep_done -> last_sleep_at / sleep_armed=False / uptime=0 / 等级回 L0（C15-26/27）
```

- 第 4 节全部 P0（C15-01/02/03/04/05/07/09/10/11/14/15/16/17/19/21/22/23/24/25/26/27/28/29/31/32/33/34/36/40）通过。

- **P1-2（每等级不同提示词 + 30 天必睡）**：提示词按等级切换且内容不同（C15-14/15）；冷却抑制（C15-17/18）；30 天硬上限 mock uptime 必触发（C15-28/29/34）。
- **P1-3（自主触发非关键词）**：关键词反证成立（C15-31/32）；自主触发证明成立（C15-33/34）。

- `sleep_targets` 不含本体行为正确（C15-35/51）；`sleep_duration_min>0` 停机-等待-启动流程（C15-36/59）；`post_sleep_notify`（C15-37/38）。
- 看门狗可用性端到端（C15-43/44/45）；时钟回拨对 uptime 影响（C15-41/42）。
