## 1. 问题陈述：自杀悖论（Self-kill paradox）

当前形态下，Guardian 是**运行在 `astrbot` 容器内的 AstrBot 插件**（`main.py` → AstrBot `Star` 生命周期）。而它的职责是**守护 `astrbot` 本体**。这两件事在结构上互斥：

| # | 失效模式 | 机制 | 后果 |
| --- | --- | --- | --- |
| S1 | **自杀后无法确认** | 睡眠/重启 `astrbot` 即杀死自己的宿主进程。`reconcile()` 永远跑不到，`on_sleep_done()` 不被调用，`forced_at` 不被清除 | 睡眠"发出去了"，但插件永远不知道成没成；下次 tick 重复发起 |
| S2 | **无法自我观察** | `self_health` 探针在 AstrBot 进程内测量 AstrBot。事件循环一旦阻塞，探针一起阻塞 | "我卡住了"这件事**无法被自己上报**；用户只看到 Bot 不回复，守护系统也哑了 |
| S3 | **睡眠窗口监控真空** | `duration_min > 0` 时 stop 掉 `astrbot` 并等待 N 分钟 | 整个窗口内**没有任何东西**在巡检——napcat 此时掉线也不会被发现 |
| S4 | **崩溃循环不可见** | 插件自身 bug 导致 AstrBot 崩溃 → 随容器重启 → 再跑同样逻辑 → 再崩 | 宿主看门狗会忠实地一次次拉起，而插件**身处循环之中**，无法判定"是我在害它" |
| S5 | **生命周期受制于人** | 调度器/巡检循环挂在 AstrBot 的插件 load/reload/terminate 钩子上（`D00` F7/F9：WebUI 重载不触发 `on_astrbot_loaded`） | 内核的存活时间不由自己决定；一次误重载即中断守护 |

**结论**：只要"大脑"和"被守护对象"在同一个进程里，S1–S5 就无法根治。**大脑必须搬出去。**

> 现有的宿主看门狗（`deploy/guardian-watchdog.py`）只解决了"执行"这一半——它能从容器外重启容器。**"决策与观察"这一半仍在容器内**，这正是本设计要补的部分。

## 2. 设计目标与不变量

### 2.1 目标

1. **内核（决策 + 观察）在 AstrBot 进程之外运行**，AstrBot 重启/崩溃/重载都不影响内核存活。
2. 内核能**独立确认**一次睡眠/重启是否真正完成（因为内核不再随之死亡）。
3. 内核能**独立观察** AstrBot 是否卡死（不再"自己测自己"）。
4. AstrBot 侧只保留**薄适配层**：注册 LLM 工具与命令、把调用转发给内核、把结果回执给用户。
5. 任一域崩溃，其余两域仍能按既定职责降级运行（见 §8 失败归属矩阵）。
6. **不削弱任何既有安全红线**（B00 §10）：白名单、冷却、熔断、dry-run、受保护容器、审计不可关。

### 2.2 不变量（Invariants，施工时不得违反）

- **I1 单写者**：`state.json` 与 `audit.jsonl` 在任一时刻**只有一个写者**——即内核。适配层不写内核业务状态。（适配层唯一例外：`kernel_health.json` 运维计数，见 §12.3.5。）
- **I2 边界不可越**：适配层**不持有** docker.sock、不做安全判定、不发动作、不跑巡检。所有动作经内核。适配层仅允许写 `kernel_health.json` 这一个受限计数文件。
- **I3 权限最小**：内核与看门狗各自只做必要的事；容器内写权限 ≠ 宿主执行权限（`B13 §9` L5）。
- **I4 失败不静默**：任何一域不可用都必须产生可见降级（日志 + 通知 + 审计），不得"看起来成功"。
- **I5 可回滚**：迁移过程中任一阶段都能退回"全部在 AstrBot 进程内"的旧形态。
- **I6 内核不依赖 AstrBot**：内核模块**禁止** `import astrbot`（已由 `tests/test_kernel_decoupling.py` 静态守卫）。

## 3. 目标架构：三进程 / 三失败域

```
┌─────────────────────────── 宿主机（systemd） ───────────────────────────┐
│                                                                         │
│  ┌── 域 A：守护内核 guardian-kernel ──────────────────────────────┐    │
│  │  独立进程 = **同栈 sidecar 容器**（D1-a 已定）                   │    │
│  │  · 调度器 patrol 循环 / 生命周期等级 / 安全层 / 状态 / 审计      │    │
│  │  · docker.sock（读状态；动作见 §12.2 决策 D2 待定）              │    │
│  │  · IPC 服务端（监听共享卷上的 unix socket，D3-a 已定）           │    │
│  └────────────────────────────────────────────────────────────────┘    │
│        ▲  IPC（请求/响应 + 事件推送）                                    │
│        │                                                                │
│  ┌── 域 B：适配层 guardian adapter（astrbot 容器内） ─────────────┐    │
│  │  AstrBot 插件 main.py：注册 LLM 工具 + /guardian 命令           │    │
│  │  · 收到调用 → 转 IPC → 取结果 → 回执                            │    │
│  │  · 无状态、无策略、无 docker 权限                               │    │
│  │  · 注入等级提示词（on_llm_request，必须留在 AstrBot 内）         │    │
│  └────────────────────────────────────────────────────────────────┘    │
│                                                                         │
│  ┌── 域 C：宿主看门狗 guardian-watchdog（oneshot） ───────────────┐    │
│  │  特权执行器 + 最后兜底：消费请求文件，执行 stop/start/restart     │    │
│  │  · 内核失能时仍能兑现最后一份已发布请求                          │    │
│  │  · 纯 stdlib，不 import AstrBot                                  │    │
│  └────────────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────────────┘
```

**三域职责一句话**：
- **A 内核**：想（决策）+ 看（观察）+ 记（状态）。**独立存活**。
- **B 适配**：说（对接 AstrBot 的对话/工具/提示词面）。**无权限、无状态**。
- **C 看门狗**：做（真正动容器）。**特权、最小、兜底**。

## 4. 进程归属与生命周期（谁启动谁 / 谁监控谁 / 谁重启谁）

| 关系 | 由谁负责 | 机制 |
| --- | --- | --- |
| 内核启动 | Docker（sidecar 容器，D1-a） | `restart: unless-stopped` |
| 内核被监控 | 域 C 看门狗（每 30s tick 检查内核心跳） | 心跳文件 `guardian/kernel_heartbeat.json`（`ts`）；超时（默认 90s）则 `docker compose restart guardian-kernel` |
| 内核被重启 | 域 C 看门狗 | 同上（**容器无法可靠地重启自己**，故此项必须留在宿主） |
| 适配层启动/停止 | AstrBot 插件管理器 | 现有 `on_astrbot_loaded` / `on_plugin_loaded`（`D00` F7 已修） |
| 适配层被监控 | 域 A 内核 | IPC 连接存活 + 适配层心跳；断开则记录"工具面不可用"并告警 |
| **`astrbot` 容器重启** | **域 A 内核直连 docker.sock**（D2-b） | 内核自行 `stop/start/restart` + 复检 `StartedAt`/健康；**不再经看门狗** |
| **`napcat` 掉线重登** | **域 A 内核直连**（D2-b） | 走 `utils/dockerclient.py`（非本体容器可直接操作） |
| **内核 docker 访问失效** | 域 A 退回 → 域 C 执行 | 内核回退"写请求文件"路径，由看门狗兑现（最后兜底） |
| `astrbot` 容器崩溃恢复 | Docker restart policy | `restart: unless-stopped`（与内核无关，内核只负责观察+告警） |
| **内核自身卡死** | 域 C 看门狗 | 心跳超时（默认 90s）→ 重启内核容器 |
| **内核挂掉且心跳未触发** | 域 B 适配层请求 → 域 C 执行 | 适配层写 `guardian/kernel_reload_request.json`（**有界**：≤1 次 + 冷却 600s，§12.3.5）；看门狗统一重启路径消费 |
| **看门狗失败** | systemd | timer 下一 tick 重试；`recovery_pending` 保留义务（`B13 §7.1`） |

> **看门狗的重启只有一条代码路径**：每 tick 检查 ① 内核心跳超时？② 有 reload 请求？任一成立即 `docker compose restart guardian-kernel`（同一段代码、同一把 flock、同一套 nonce 去重）。这样"心跳守护"与"适配层请求"不会并发打架。

**关键结论**：**"重启 `astrbot`"不再是一次自杀**——发起者是域 A（独立进程），它能亲眼看到 `astrbot` 的 `StartedAt` 更新并复检健康，然后调用 `on_sleep_done()` 清除 `forced_at`。**S1 被根治。** 而 D2-b 让这个"亲眼看到"的闭环**没有 30s 的 timer 延迟**——执行完立即复检，这正是内核搬出去的收益兑现处。

| 归属 | 内容 | 约束 |
| --- | --- | --- |
| **内核（域 A）** | 配置加载、状态存储、审计、事件总线、探针注册、引擎、调度器、安全层、生命周期策略、通知**内容**生成、动作执行（经看门狗或直连） | 禁止 `import astrbot`（I6） |

### 5.3 装配层如何拆

`runtime.py` 按职责一分为二：

- `kernel_runtime.py`（域 A）：装配 `GuardianConfig` / `StateStore` / `AuditLog` / `EventBus` / `HealthEngine` / `Scheduler` / `SafetyGuard` / `DockerClient` / `NapCatClient` / `Ros2Runner`。**移除** AstrBot 依赖（logger 走 `core.log`；数据目录改为"内核自己的数据目录"；通知改为"生成文本 + 交给适配层发送"）。
- `adapter_runtime.py`（域 B）：保留 `MessageChain`/`Plain` 消息体构造、`StarTools` 数据目录解析、AstrBot 侧通知投递。

## 6. IPC 与鉴权

### 6.1 传输（**D3-a 已定**：Unix socket 优先，TCP 回退）

| 方案 | 适用 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **Unix domain socket**（共享卷，如 `/AstrBot/data/guardian/kernel.sock`） | 内核 sidecar 或 host 服务 | 不经网络栈；文件权限即可鉴权；天然"本机限定" | Windows 宿主不可用；需共享卷 |
| **localhost TCP**（如 `127.0.0.1:6198`，仅绑定 loopback） | 内核与适配层同宿主 | 简单、跨平台 | 需额外 token 鉴权；端口管理 |

**已选 D3-a**：Unix socket 优先，TCP 回退（与 `docker.socket_path` 的"优先 socket、可降级"风格一致）。因 D1-a 选了同栈 sidecar，socket 落在两者共享的 `./data` 卷上即可。

### 6.2 协议

换行分隔的 JSON-RPC 2.0（每行一条消息），双向：适配层发 `request`，内核回 `response`；内核可主动推 `event`（如"即将睡眠"通知）。

```jsonc
// 请求（适配层 → 内核）
{"jsonrpc":"2.0","id":7,"method":"health_report","params":{"scope":"all"}}
// 响应（内核 → 适配层）
{"jsonrpc":"2.0","id":7,"result":{"text":"...","structured":{...}}}
// 错误
{"jsonrpc":"2.0","id":7,"error":{"code":"safety_denied","message":"目标不在白名单"}}
// 事件（内核 → 适配层，无 id）
{"jsonrpc":"2.0","method":"notify","params":{"text":"[睡眠] 即将执行...","severity":"warn"}}
```

### 6.3 鉴权

- Unix socket：`chmod 0660` + 属组限定（只挂给内核与 `astrbot`）。
- TCP：启动时内核生成随机 token 写入共享卷 `kernel.token`（`0600`），适配层读取并在每个请求带 `Authorization`。**不硬编码、不写日志**。

### 6.4 超时与降级（I4 + D4-a+ 阶梯）

| 场景 | 行为 |
| --- | --- |
| 适配层连不上内核 | 进入 **D4-a+ 有界自修复阶梯**（§12.3.5）：静默重连 → 请求一次内核重载 → 宽限期 → 仍失败才显式失败 |
| 内核响应超时（默认 10s） | 返回"内核响应超时"；**不重试破坏性动作**（避免重复执行） |
| 适配层重启 | 自动重连；内核无需感知（无状态连接） |
| 内核重启 | 适配层重连；期间工具不可用，恢复后自愈 |
| 自修复额度耗尽 | 进入 `kernel_degraded`，四层显式失败；`/guardian reset` 或稳定 300s 自动复位（§12.3.5 C4） |

## 8. 失败归属矩阵

| 域挂掉 | 后果 | 谁负责恢复 | 降级表现 |
| --- | --- | --- | --- |
| **适配层**（AstrBot 插件） | LLM 工具/命令不可用 | AstrBot 插件管理器 | 对话面失去工具，但**内核仍在巡检、动作、告警**（告警由内核直接投递或写审计） |
| **内核** | 无决策、无观察、无动作 | 看门狗（心跳超时 → 重启内核容器） | 看门狗仍能兑现最后一份已发布请求；期间无新巡检。**适配层显示"内核不可用"（D4）** |
| **看门狗** | **仅**失去"内核心跳守护"与"最后兜底" | systemd timer 重试 | **因 D2-b，内核仍能直连 docker.sock 执行全部动作**——守护能力基本不受影响；仅当内核 docker 访问也失效时才降级为只告警 |
| **`astrbot` 容器** | Bot 下线 | Docker restart policy | 内核观察到 `container_health=crit`，复检恢复后通知 |
| **`napcat` 容器** | QQ 掉线 | 内核发起重登 | 内核直接操作（非本体） |
| **docker daemon** | 全部容器动作失效 | 运维 | `docker_daemon` 探针转 `crit`；内核降级告警不崩溃（`D00` V-list A9） |

## 9. 迁移计划（分阶段，每阶段可独立验收与回滚）

| 阶段 | 内容 | 验收 | 回滚 |
| --- | --- | --- | --- |
| **M0（已完成）** | 内核模块解耦：`core/log.py` facade + 移除全部 `import astrbot`；`test_kernel_decoupling.py` | 3/3 通过 | 无（纯内部重构） |
| **M1** | 拆 `runtime.py` → `kernel_runtime.py` + `adapter_runtime.py`；装配层去 AstrBot 依赖 | 内核可在无 astrbot 的解释器里构造并跑一轮 patrol | 保留 `runtime.py` 作为兼容壳 |
| **M2** | 内核 IPC 服务端 + 适配层客户端；工具/命令改走 IPC | 契约测试（§10 全 method）；断连降级可见 | 配置开关 `kernel.mode=inproc` 回退旧路径 |
| **M3** | 内核独立进程化：新增入口 `python -m astrbot_plugin_guardian.kernel`（或 sidecar 容器 / systemd 单元） | 独立进程能跑 patrol + 心跳 | 停止独立进程，回到 `inproc` |
| **M4** | 看门狗增加内核心跳守护；数据目录迁移 | 杀内核 → 看门狗 30s 内重启；迁移幂等 | 保留旧数据目录只读副本 |
| **M5** | **动作直连化（D2-b 已定）**：内核直接操作 `astrbot`/`napcat` 容器并自行复检 `StartedAt`+健康；看门狗职责收窄为"内核心跳守护 + 最后兜底" | 真机 1 分钟睡眠：内核观察到 stop→start→健康，`on_sleep_done()` 被调用、`forced_at` 被清除 | 配置开关 `kernel.direct_actions=false` 回到"经看门狗"路径 |

> **强制流程（`D00` F9）**：每次同步代码后必须**重载/重启 + 正向信号确认**，不得只信"重载成功"。

## 11. 安全影响

内核独立后**拥有 docker.sock**（无论 sidecar 还是 host 服务），这是权限的集中点。缓解：

1. **只读优先**：状态查询走只读；动作只走白名单枚举（`B00 §10`）。
2. **内核不暴露到网络**：IPC 仅 loopback / Unix socket；内核自身不监听 `0.0.0.0`。
3. **权限已按 D2-b 重新分配，边界收紧**：`docker.sock` 从"接收 LLM/用户输入"的 `astrbot` 容器，挪到"不接受未受信输入"的内核容器；适配层（真正的暴露面）**无** docker 权限。代价是 `B13 §9` L5 的"宿主侧再校验"环节弱化——补偿措施：① 内核只接受结构化 IPC（无自由文本命令）；② 动作仍过内核内安全层（白名单/冷却/熔断/dry-run）；③ 看门狗保留"最后兜底"路径，内核 docker 访问异常时可退回写请求文件；④ 内核容器用最小 socket 权限 + `group_add` 收敛，不用 `privileged`。
4. **审计不可关**：所有动作（含被拒）仍写 `audit.jsonl`（单写者=内核）；IPC 断连另写 `adapter_events.jsonl`（单写者=适配层，见 §12.3.3 L3）。
5. **不引入任意 shell**：内核与看门狗都只调用枚举化的 docker 子命令。

### 12.2 D2（✅ 已定：D2-b 直连）—— 内核如何执行"特权动作"？

**先定义"动作"**。Guardian 注册了 8 个 action（`@register_action`），按是否产生**容器/进程级副作用**分为两类：

| action kind | 物理副作用 | 走什么 | 属 D2 讨论范围？ |
| --- | --- | --- | --- |
| `restart_container` | Docker Engine `restart <容器>` | docker.sock / 看门狗 | ✅ 是 |
| `start_container` | Docker Engine `start <容器>` | docker.sock / 看门狗 | ✅ 是 |
| `sleep` | Docker Engine `stop → 等待 → start`（或 `restart`） | docker.sock / 看门狗 | ✅ 是（**核心**） |
| `qq_relogin`（`restart_container` 法） | Docker Engine `restart napcat` | docker.sock / 看门狗 | ✅ 是 |
| `qq_relogin`（`webui_quick_login` 法） | HTTP 调 NapCat WebUI | 内核直发 HTTP | ❌ 否（不碰 Docker） |
| `ros2_restart` | 白名单 shell 命令 / `docker exec` | 内核本地执行 | ⚠️ 部分（`docker exec` 需 docker 访问） |
| `notify` | 无（发消息） | 内核生成文本 → 适配层发送 | ❌ 否 |
| `set_mode` / `set_profile` | 无（改配置） | 内核内部 | ❌ 否 |

**所以 D2 问的是**：上表前 4 类（+ `ros2_restart` 的 `docker_exec` 后端）——内核要真正"动容器"时，走哪条路？

| 选项 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **D2-a 经宿主看门狗** | 内核写 `restart_request.json` → 宿主 systemd oneshot 执行 `docker compose stop/start/restart` | 保留 `B13 §9` L5 不变量（**容器内写权限 ≠ 宿主执行权限**）；复用已测试的 v2 协议（60 项用例）；内核无特权 | 延迟 ≤1 个 timer 周期（30s）；多一跳；内核容器**不需要**挂 docker.sock，但**仍需**挂 socket 用于只读探针 |
| **D2-b 内核直连 docker.sock** | 内核自己调 Engine API / docker CLI，并自行复检 `StartedAt` + 健康 | "执行→确认"闭环最短——这正是把内核搬出去的**全部意义**；无 30s 延迟；少一跳 | 内核容器需挂 `docker.sock`（等价于今天的 `astrbot`，只是挂载对象换了）；L5 不变量的"宿主侧再校验"环节消失 |

> **推荐：D2-b（直连），但保留看门狗做两件不可替代的事。**
> 1. **内核心跳守护**：容器**无法**可靠地重启自己（自杀式重启后无法保证回来），所以"内核卡死 → 重启内核"必须由宿主看门狗负责（§4）。
> 2. **最后兜底**：内核的 docker 访问若失效（如 socket 权限变更），内核可退回"写请求文件"路径。
>
> **为什么 D2-b 的权限边界反而更好**：今天 `docker.sock` 挂在 `astrbot` 容器上——而那个容器**接收 LLM 与用户输入**（`guardian_restart_container` 的参数就来自 LLM）。迁移后 `docker.sock` 挂在内核容器上，内核**不接受任何未受信输入**（只接受来自适配层的结构化 IPC，且 IPC 本身过安全层），适配层（真正的暴露面）反而**没有** docker 权限。**这是比现状更紧的边界，不是更松。**

### 12.3 D4（✅ 已定：D4-a+）—— 内核不可用时，失败"显示到哪"？

#### 12.3.1 先界定：这个"失败"指的是什么？

**D4 的"失败" = 「适配层无法完成一次 IPC 调用」**，即**可用性（availability）问题**，而**不是**业务结果问题。

**它不管**下面这些——这些是**正常业务结果**，走既有的审计 + 通知路径，与 D4 无关：
- 内核**有响应**但动作被安全层拒绝（`safety_denied` / `not_allowlisted` / `protected` / `cooldown`）
- 内核**有响应**但动作执行失败（宿主握手 `status=failed` / `recovery_pending`）
- 内核**有响应**但参数非法（`bad_target`）

**它管**的是"连不上 / 没响应 / 连上但内部崩了"，根因有 6 类，**不只是"内核挂掉"**：

| # | 根因 | 内核还活着吗 | 能否自愈 | 谁负责 |
| --- | --- | --- | --- | --- |
| R1 | **内核进程/容器挂了**（crash / OOM / 被误杀） | ❌ 死 | ✅ | 看门狗（`restart: unless-stopped` + 心跳守护） |
| R2 | **内核活着但卡死**（event loop 阻塞 / 死锁 / 长时间 GC） | ⚠️ 假活 | ✅ | 看门狗（心跳超时 → 重启内核容器） |
| R3 | **内核正在重启的窗口**（部署/升级/被看门狗拉起） | ⚠️ 瞬断 | ✅ | 适配层退避重连 |
| R4 | **IPC 通道坏了但内核活着**（socket 文件被删 / 权限变更 / 共享卷未挂上 / 两端路径配置不一致） | ✅ 活 | ❌ **不会自愈** | **人**（必须靠 L1 的诊断线索一眼定位） |
| R5 | **启动竞态**（适配层先起，内核还没 listen） | ⚠️ 未就绪 | ✅ | 适配层退避重连 |
| R6 | **内核活着但拒绝服务**（过载 / 内部未捕获异常） | ✅ 活 | ⚠️ 可能 | 内核自身；持续则看门狗重启 |

> **R4 是唯一不会自愈的一类**，也是 L1 必须携带**诊断线索**（socket 路径、`errno`、最后心跳时间戳）而非只丢一句"不可用"的原因——否则用户/运维无法区分"内核死了在等看门狗"和"通道配错了永远好不了"。

#### 12.3.2 关键澄清：**内核挂掉 ≠ AstrBot 挂掉**，两者由不同的当事方显示

| 谁挂了 | 谁能显示 | 显示什么 |
| --- | --- | --- |
| **内核挂掉**（R1–R6） | **适配层**（它活在 AstrBot 里，还能说话） | "守护内核不可用" + 诊断线索（**这就是 D4 要解决的**） |
| **AstrBot（含适配层）挂掉** | **内核**（它独立存活，还在观察） | `container_health=crit` 告警 + 恢复通知（**这正是 S2 的收益**） |

两者互为对方的"观察者"——**没有任何一方是单点盲区**。如果两者同时挂（如宿主宕机），由看门狗/systemd 兜底。这也是为什么三域必须互相独立。

#### 12.3.3 显式失败的落点：4 个面

**显式失败必须落到 4 个面**（否则就是 §2.2 的 I4"失败不静默"被违反）：

| 层 | 位置 | 具体表现 | 谁负责 |
| --- | --- | --- | --- |
| **L1 对话面（用户直接可见）** | AstrBot 聊天窗口 | 命令 `/guardian <任意>` → 立即返回错误文本，**不假装成功**；LLM 工具 → 返回结构化错误（`{"error":"kernel_unavailable","last_heartbeat":...}`），由 LLM 转述给用户 | 适配层 |
| **L2 日志面** | `docker logs astrbot` | `logger.warning/error` 打出 IPC 断开/重连时间线 + 最后心跳时间戳 | 适配层 |
| **L3 审计面** | 共享卷 `guardian/adapter_events.jsonl` | **适配层自己的**事件流，记录 `ipc_disconnected` / `ipc_reconnected` / `kernel_unreachable`。**注意**：主 `audit.jsonl` 由内核单写者持有（I1），内核挂了写不了，所以断连事件必须由适配层另开一条流 | 适配层 |
| **L4 主动通知** | 用户会话（`notify.umo_list`） | 内核掉线超过阈值（如 90s）→ 适配层**主动**推送一条告警 | 适配层 |

> **L4 有个递归陷阱必须点破**：正常告警由内核产生、适配层发送。**如果内核就是挂掉的那个，内核无法产生"我挂了"这条告警。** 所以必须**显式指派**：适配层恒定负责**唯一一条**告警——"守护内核不可用"。这也是 D4 选 (a) 而非 (b) 的关键理由：适配层至少要保留这一点点"兜底判断"能力，不能纯粹做转发。

#### 12.3.4 L1 错误码（用户实际会看到的话）

适配层必须把"不可用"细分到**可诊断**的程度，而不是笼统一句"出错"：

| code | 触发（对应 §12.3.1 根因） | 用户看到的话 | 能否自愈 |
| --- | --- | --- | --- |
| `kernel_unavailable` | socket 不存在 / `ECONNREFUSED`（R1/R3/R4/R5） | "守护内核不可用：IPC 通道未建立（socket=`…/kernel.sock`，errno=`ECONNREFUSED`，最后心跳 21:03:41）" | 多数可，R4 不可 |
| `kernel_timeout` | 连上但 10s 无响应（R2/R6） | "守护内核无响应（超时 10s），可能正在重启或被阻塞" | ✅ |
| `kernel_busy` | 有响应但显式拒绝（R6 过载） | "守护内核繁忙，请稍后重试" | ✅ |
| `kernel_error` | 有响应但返回内部错误（R6） | "守护内核内部错误：`<detail>`" | ⚠️ |

> **判据**：`kernel_unavailable` 与 `kernel_timeout` 必须携带 `last_heartbeat` 时间戳。若"最后心跳"距现在 < 30s，说明内核刚还活着 → 大概率是 R4（通道）或 R3（重启窗口）；若已 > 90s → 大概率是 R1（死了），应同时触发 L4 主动告警。

#### 12.3.5 ✅ 已定：**D4-a+ 有界自修复阶梯**（用户方案）

> 用户方案：**内核挂掉先尝试重载内核自修复一次，不行再走 D4-a 显式失败。** 采纳。这补上了纯 D4-a 的短板——在打扰用户之前先给一次自救机会。但必须**有界**，否则会退化成 S4（崩溃循环）的翻版。

**阶梯（自上而下，逐级升级）：**

```
适配层检测到 IPC 调用失败
  │
  ├─ Stage 1  快速重连（静默，不打扰任何人）
  │     指数退避重连：0.5s → 1s → 2s → 4s → 8s（合计 ~15s）
  │     覆盖根因 R3（重启窗口）/ R5（启动竞态）
  │     ✅ 成功 → 静默恢复（仅审计记 ipc_reconnected）
  │
  ├─ Stage 2  请求一次内核重载
  │     适配层写 guardian/kernel_reload_request.json
  │       {nonce, ts, reason, attempt:1, last_heartbeat}
  │     前置闸门（两者都满足才发）：
  │       ① attempt < kernel.max_auto_reloads（默认 1 —— 用户说的"一次"）
  │       ② now - last_reload_ts > kernel.reload_cooldown（默认 600s）
  │     看门狗消费该请求 → docker compose restart guardian-kernel
  │
  ├─ Stage 3  重载后宽限期
  │     等待 kernel.reload_grace_sec（默认 90s）：容器起 → listen → 首次心跳
  │     ✅ 成功 → 静默恢复（审计记 kernel_reloaded_ok，并启动"稳定计时"）
  │
  └─ Stage 4  仍失败 → 判定自修复失败 → 走 D4-a 四层显式失败
        进入 kernel_degraded 状态（人工介入）
        ⛔ 不再自动重载，直到：
           · 用户执行 /guardian reset（清零 attempt），或
           · 适配层观察到内核心跳恢复并稳定 ≥ kernel.reload_reset_sec（默认 300s）
             → 自动复位计数，为下一次故障留出额度
```

**四条硬约束（防循环，缺一不可）：**

| # | 约束 | 值 | 为什么 |
| --- | --- | --- | --- |
| C1 | **次数有界** | `kernel.max_auto_reloads = 1` | 无界重载 = S4 崩溃循环。用户明确要"一次" |
| C2 | **冷却间隔** | `kernel.reload_cooldown = 600s` | 防"内核反复崩"时高频重启把宿主拖垮 |
| C3 | **失败即停手** | 一次重载后仍不通 → 转人工 | 与 `B00 §10` 第 6 条"失败即停"同源 |
| C4 | **额度自动复位** | 稳定 `reload_reset_sec = 300s` 后清零 | 否则"一次"会变成永久一次性，后续真故障无法自救 |

**谁执行重载？** 必须由**看门狗**执行，不能让内核自己重载自己（容器无法可靠地重启自己，§4）。因此：

- 适配层**只写请求文件**（`kernel_reload_request.json`），**不直接重启**任何东西——适配层无 docker 权限（D2-b 后的权限分配）。
- 看门狗**统一重启路径**：每 tick 检查 ① 内核心跳超时？② 有 reload 请求？——**任一成立即重启内核容器**，同一段代码、同一把 flock、同一套 nonce 去重。**避免"心跳守护"与"适配层请求"两条路并发重启打架。**

**计数写在哪个文件？** `guardian/kernel_health.json`（**适配层单写者**）。

> ⚠️ **这里必须诚实修正不变量 I2**：I2 原文"适配层不写状态"。但内核挂了它就写不了，所以"故障计数"只能由还活着的适配层维护。**修正后的 I2**：适配层不写**内核业务状态**（`state.json` / `audit.jsonl`），**仅允许**写 `kernel_health.json` 这一个受限的运维计数文件（字段固定：`attempt` / `last_reload_ts` / `last_heartbeat_seen`）。
