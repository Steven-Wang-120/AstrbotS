### 2.2 QQ 自动登录（正面结论）

NapCat 启动日志：

```
10-14 10:35:22 [info] 正在快速登录  2186059326        <-- 快速登录，全程无二维码
10-14 10:35:24 [info] WebSocket反向服务: ws://astrbot:6199/ws, : 已启动
10-14 10:35:24 [info] [AdapterManager] OneBot11 适配器初始化完成
```

AstrBot 启动日志：

```
[10:35:24.325] aiocqhttp(OneBot v11) 适配器已连接。
```

**根因说明**：原先每次启动都出二维码，是因为 `compose.yml` 没给 `napcat` 传 `ACCOUNT`，
NapCat entrypoint 只在 `ACCOUNT` 非空时才以 `qq --no-sandbox -q <号>` 启动。补上
`NAPCAT_ACCOUNT=2186059326` 后即恢复快速登录（本机有本地会话时秒登，否则退化为扫码）。

### 2.3 一个必须知道的环境限制

**NapCat `astrbot` 模板没有开启 OneBot 11 HTTP 服务（3000 端口拒连）**：

```
NapCat 不可达(http://napcat:3000): Cannot connect to host napcat:3000
```

因此插件的 QQ 探测第一条证据链（`get_status` / `get_login_info`）在本环境**永久不可用**。
另外 NapCat entrypoint 每次启动都会用 `/app/templates/astrbot.json` 覆盖 `/app/onebot11.json`，
所以改宿主机配置无效，必须改容器内模板（镜像重建会丢）——这一点直接决定了 F11 的修法选择。

## 3. 缺陷清单

### F1 导入路径错误 —— 插件完全无法加载（已修复）

- **现象**：`ImportError: cannot import name 'EventMessageType' from 'astrbot.api.event'`，插件 0 条日志、0 个工具注册。
- **根因**：AstrBot 4.2x 把 `filter` 拆成独立子模块，`filter` / `EventMessageType` / 各装饰器都在 `astrbot.api.event.filter` 下，不在 `astrbot.api.event`。
- **修复点**：`main.py` 改为 `from astrbot.api.event.filter import EventMessageType`，并用 `try/except ImportError` 兼容旧布局。
- **复现/回归**：`tests/audit_astrbot_api.py` 逐模块 import 校验（49/49 通过）。

### F2 `event.message_str` 属性不存在（已修复，潜伏缺陷）

- **现象**：`/guardian` 命令一调就 `AttributeError`。
- **根因**：4.x 只有方法 `get_message_str()`，没有 `.message_str` 属性。
- **修复点**：新增 `_event_text(event)` 跨版本助手，优先走 `get_message_str()`，回退 `message_str`。
- **回归**：`tests/live/cmd_probe.py` 两条断言分别覆盖方法路径与旧版属性回退。

### F3 配置 schema 用了不支持的 `dict` 类型（已修复）

- **现象**：`TypeError: 不受支持的配置类型 dict`，来自 `AstrBotConfig._config_schema_to_default_config`，插件配置直接加载失败。
- **根因**：`_conf_schema.json` 中 `ros2.node_restart_commands` / `ros2.env` 写成 `"type": "dict"`；4.26.7 只支持 `int/float/bool/string/text/list/file/object/template_list`。
- **修复点**：两处改为 `"type": "object"`；同时给 `lifecycle.levels` 补 `default` 数组，让 WebUI 直接显示 L0–L4 而不是空列表。

### F4 `AuditLog.append()` 必填参数打死了文档化的调用路径（已修复）

- **现象**：每轮巡检都崩，日志连续刷
  `任务 guardian:patrol 执行失败: AuditLog.append() missing 1 required keyword-only argument: 'kind'`（10:58–11:37 共约 34 轮全挂）。
- **根因**：`core/audit.py` 把 `kind` 设成无默认值的关键字参数，而 `engine._record_incident()` 走的是文档里的 `append(incident=...)` 分支，不传 `kind` → `TypeError`。**只要巡检产生任何 finding，整轮就崩**，等于巡检引擎对"发现问题"这一种情况完全失效。
- **修复点**：`kind` 给默认值 `""`，并在 `incident is not None` 时 `kind = kind or "incident"`，两种调用风格都通。

### F5 容器白名单误伤逻辑目标，QQ 自动重登永远不可能触发（已修复）

- **现象**：审计日志连续 `action.denied` / `not_allowlisted`，detail 为 `qq_relogin: 目标 qq 不在动作白名单内（managed ∪ allowed_containers）`。
- **根因**：`qq_relogin` 的目标是逻辑名 `"qq"`（真实作用对象由 `qq.relogin_method` 决定，本环境为 `restart_container`），却被拿去和容器名白名单比对。
- **修复点**：`core/safety.py` 新增 `LOGICAL_TARGET_KINDS = {"qq_relogin", "ros2_restart"}` 与 `_authorize_logical_target()`：`relogin_method == disabled` → `relogin_disabled`；`webui_quick_login` 但没配 `webui_base` → `relogin_no_webui`；ROS2 节点不在 `node_restart_commands` → `ros2_no_command`。
- **回归**：`tests/live/safety_probe.py` 8/8。

### F6 QQ 探测把"无法判定"当成"确认掉线"（已修复，最危险的一项）

- **现象**：QQ 实际在线，插件却报 `CRIT QQ 已掉线` 并触发重登动作。
- **根因**：两条证据链（OneBot HTTP `get_status` / `get_login_info`）都连不上时，代码把异常当成"不在线"证据，直接进掉线计数。
- **修复点**：`probes/qq_login.py` 引入 `definitive` 标志；无任何确定性证据时返回 `Status.UNKNOWN` + `detection_degraded=True`，**不进掉线计数、不触发重登**。
- **回归**：容器内构造真实 `NapCatUnavailable` 异常，确认走高危分支而非基类兜底；`qq_fail_streak == 0`。

### F7 WebUI 重载插件后守护系统"看起来成功、实际没跑"（已修复）

- **现象**：WebUI 显示"重载成功"，但没有任何巡检日志。
- **根因**：`@filter.on_astrbot_loaded()` 只在 AstrBot 框架启动时派发一次；在 WebUI 里重载插件不会重新触发它。
- **修复点**：补 `@filter.on_plugin_loaded()` 兜底启动运行时。
- **回归**：重载日志出现 `hook(on_plugin_loaded) -> astrbot_plugin_guardian - on_plugin_loaded`，随后巡检立即恢复。
- **附带修复 F7b**：`validate_target()` 改成 kind 感知 —— ROS2 节点名以 `/` 开头，原 `TARGET_RE` 拒绝前导 `/` 导致 `ros2_restart` 永远 `bad_target`；新增 `ROS2_NODE_RE`。

### F8 `StarTools.get_data_dir()` 在子模块里解析失败，数据写到野路径（已修复）

- **现象**：数据目录落到 `/AstrBot/data/plugins/data`（非标准位置），`state.json` / `audit.jsonl` 不在插件数据目录下。
- **根因**：`StarTools.get_data_dir()` 依赖调用栈帧反查插件名，从 `runtime.py`（子模块）调用时 `RuntimeError: Unable to resolve metadata for module ...`，被静默兜底。
- **修复点**：`resolve_data_dir()` 显式传插件名 `astrbot_plugin_guardian`，二级回退 `get_astrbot_data_path()/plugin_data/<name>`。
- **回归**：启动日志确认 `数据目录=/AstrBot/data/plugin_data/astrbot_plugin_guardian`。

### F9 改了代码却"不生效"—— 同步与重载的时序坑（流程缺陷，非代码）

- **现象**：`audit.py` 磁盘上已是修复版（`kind=""` 默认值，容器实测签名带 `incident` 参数），但巡检**仍在报 F4 的旧 TypeError**，持续 50 分钟。
- **定位过程**：
  1. 全新进程 import `astrbot_plugin_guardian.core.audit` → 签名正确 → 排除磁盘代码问题；
  2. 全盘只找到一份 `audit.py`、无 `__pycache__` → 排除重复模块与字节码缓存；
  3. `stat` 容器文件 mtime = **11:23:05**，而最后一次插件重载在 **11:02:03** → **真相：代码同步发生在重载之后，运行中的进程一直在跑旧代码**。
- **已核实的重载语义**（`star_manager.py`）：`reload()` → `_terminate_plugin()` → `_unbind_plugin()` → `_purge_modules(root_dir_name=...)`，会删掉 `sys.modules` 里 `data.plugins.astrbot_plugin_guardian.*` 全部子模块，且 `_unbind_plugin` 受 `if smd.name and smd.activated:` 保护（star_manager.py:1062）。**所以重载本身是能刷新子模块的，问题纯粹在时序。**
- **修复点（流程）**：任何文件同步后**必须**重载，且必须用一个**正向信号**确认生效（例如"巡检日志出现预期内容"），不能只信 WebUI 返回的"重载成功"。
- **验证**：11:51 重载后巡检立即恢复 `ok=True`，F4 报错彻底消失。

### F10 `qq_fail_streak` 只增不减、UNKNOWN 路径不清零（未修复）

- **现象**：`state.json` 里 `qq_fail_streak = 45`——这个值是 F6 修复前那波误报攒下来的，**至今没有清掉**。
- **根因**：`probes/qq_login.py` 只在 `online` 为真时清零（L88–90）；走 UNKNOWN 分支时 streak 原样保留（L106–108 只读不写）。本环境第一条证据链永久不可用，所以永远等不到 `online=True` 来清零。
- **影响**：
  1. 抖动抑制窗口被作废——下一次真掉线会**立刻**触发重登，`offline_confirm_rounds` 形同虚设；
  2. `/guardian status` 向用户展示一个毫无意义的 45；
  3. 插件重启后旧值被继续加载，跨会话污染。
- **修复点**：UNKNOWN 分支对 streak 做衰减或直接清零；`runtime.start()` 时把超过阈值的残留夹到 0；`/guardian` 提供手动清零入口。

### F11 唯一可用的 QQ 证据链没接进判定（未修复）

- **现象**：明明有第三条证据链，`/guardian` 却永远只能说"无法判定"。
- **根因**：`probes/qq_login.py` L84–85 算了 `metrics["evidence_activity"]`（来自 `main.py observe_message → runtime.note_event()` 写入的 `last_event_age`，链路是通的、实测在写），但 L92 的判定是 `online = metrics["evidence_status"] or metrics["evidence_login"]`——**第三条链路算了却不用**。文件注释还写着"证据 3"，纯误导。
- **影响**：在本部署（无 OneBot HTTP）里 QQ 探测能力为 0；只有"活跃度"这一条真能工作的证据被浪费。
- **修复点（二选一，推荐前者）**：
  - **A（推荐）**：把"最近 N 分钟内有消息事件"作为有效弱正据纳入 `online`——能持续收到消息本身就证明协议端活着。同时把 `evidence_activity` 的语义在注释里改清楚（它是"协议端活跃度"，不是"登录态"）。
  - **B**：给 NapCat 开 OneBot 11 HTTP（注意 entrypoint 每次启动覆盖 `onebot11.json`，需改容器内 `/app/templates/astrbot.json`，镜像重建会丢）或接入 NapCat WebUI `POST /api/QQLogin/GetQQLoginInfo` 作为新证据链。

### F12 泄漏检测的回归窗口只有 ~10 分钟，"斜率外推"毫无统计意义（未修复）

- **现象**：`astrbot-local 内存增长 242.0MB/h 超过阈值 80MB/h（疑似泄漏）`，每 ~2 分钟报一次。
- **根因**：`container_memory.py` 的样本环是 `window = window[-cfg.samples:]`，`samples=10`，而巡检间隔 ~66s → **整个回归窗口只覆盖 10.2 分钟**。用 10 分钟的最小二乘斜率乘 3600 外推成 MB/h，末端一点噪声就被放大：一个 3MB 的瞬时抖动读数约 18MB/h，真实爬坡直接读出 242MB/h。
- **修复点**：样本环按**时间**留存（≥30–60 分钟，时间抽稀），判定要求"斜率超限 **且** 窗口内总涨幅 ≥ 下限 **且** 连续 K 轮命中"，三者同时满足才报警。

### F13 内存口径在 cgroup v2 上完全错（未修复，硬伤，F12 误报的直接原因）

- **现象**：`state.json` 里 `astrbot-local` 的样本在相邻两轮巡检之间**锯齿式跳变**，~468MB ↔ ~577MB 交替：

```
12:05:16  577.47 MB
12:06:20  466.34 MB
12:07:26  577.95 MB
12:08:30  467.79 MB
12:11:48  576.15 MB
```

  而 `docker stats` 实测 `astrbot-local 458.6MiB`（稳定，napcat-local 302.1MiB），**根本没有泄漏**。
- **根因（从容器内直连 Docker Engine API 取到铁证）**：
  ```
  usage          = 509.3 MB
  stats.cache    =   0.0 MB     <-- 恒为 0
  stats.rss      =   0.0 MB     <-- 恒为 0
  stats.anon     = 456.9 MB     <-- 稳定，三次采样 140s 内不变
  stats.file     =  28.0 MB
  usage - cache  = 509.3 MB     <-- 探针实际取到的值
  usage - file   = 481.3 MB
  ```
  这台 Docker 跑在 **cgroup v2** 上，而探针写的 `effective = usage - stats.cache` 是 **cgroup v1 的字段名**。v2 下 `stats.cache` / `stats.rss` **根本不填，恒为 0**，于是 `effective` 退化成了**未扣 page cache 的原始 `usage`**（509MB）。原始 usage 含 ~50MB 可回收文件缓存，内核不定期回收 → 采集序列本身就在 ±110MB 锯齿，F12 的短窗斜率再把锯齿拟合出一条陡升直线。**扣缓存这个设计意图，在 v2 上等于没实现。**
- **影响**：
  1. 每 ~2 分钟一条假"疑似泄漏"告警，告警泛滥（审计日志里已刷了十几条）；
  2. 一旦打开 `allow_self_restart`，这个假斜率会驱动**每 2 分钟重启一次 Bot**，直接变成自伤；
  3. `warn_mb` / `crit_mb` 阈值也是对着错误的量在判（对着含文件缓存的 509MB 判，而不是真实的 457MB）。
- **修复点**：
  ```python
  # cgroup v2 优先取 anon；v1 回退 usage - cache / rss
  anon = st.get("anon") or 0
  if anon:
      effective = anon
  else:
      cache = st.get("cache") or st.get("rss") or 0
      effective = max(0.0, usage - cache)
  ```
  同时把 `warn_mb` / `crit_mb` 的语义改名为"匿名内存"并在文档里写清楚口径。修完后 `astrbot-local` 应稳定在 ~457MB、锯齿消失、`growth_mb_per_hour` 回到个位数。
